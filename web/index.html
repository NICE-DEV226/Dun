A programmable HTTP data plane,
written in Go.

Dun routes and proxies HTTP traffic through a small trusted Go core. Application-specific behavior runs in capability-scoped WebAssembly extensions — sandboxed, limited, and reloadable without taking traffic down.

Run the gateway Source on GitHub
dun-gateway / shell
go run ./examples/gateway/backend &
go run ./cmd/dun run -config examples/gateway/dun.yaml
curl -i localhost:8080/api/hello

How it works

Three moving parts: a YAML description of routes and plugins, a trusted Go data plane, and Wasm guests that only see the host functions they were granted.

  1. 01

    Declare routes and plugins

    One dun.yaml describes listeners, route matching, upstreams and plugin artifacts with their capabilities and resource limits.

  2. 02

    Requests cross the sandbox boundary

    Each plugin runs inside its own Wasm instance per request — or a bounded pool for artifacts proven safe to reset. Decisions (continue, respond, reject, error) are explicit integers.

  3. 03

    Observe and reload

    /healthz, /readyz and Prometheus /metrics report core and per-plugin health. Plugin binaries hot-reload atomically: compile first, swap second, drain nothing.

Architecture

A narrow trusted path. The extension boundary is explicit: capabilities are granted per plugin, enforced twice — at load time against deployment policy, and at instantiation by simply not exporting ungranted host functions.

Isolation

Fresh Wasm instance per request by default; opt-in pooling for artifacts whose state can be provably reset. Memory, timeout and concurrency are bounded per plugin.

Capabilities

Two-stage enforcement: manifests checked against deployment policy at load; ungranted host functions absent at instantiation.

Failure model

Traps, timeouts, cancellations and host-call errors are classified (trap, timeout, cancelled, …), recorded per plugin, contained — the core keeps serving.

Evaluation

Pipeline-level benchmarks isolate the extension boundary: the same machinery runs a native Go extension or a Wasm-backed one performing identical work — one response-header write. Methodology in docs/BENCHMARKS.md.

Table 1 — cost per extension invocation. Wasm is ~50–150× native; pooling recovers ~3–4× of that. End-to-end the tax is ~0.3–0.4 ms per request — small against real network latency. Under concurrency, pooled instantiation measures ~153µs/op vs ~215µs/op per-request.

Finding. Wasm buys isolation and language freedom, not speed. For header-scale work it is a defensible trade; for microsecond-critical paths a native extension remains the right boundary. The honest cost is published rather than hidden.

Reproduce

Requirements: Go 1.27+, no cgo, no external services for the tests.

shell
git clone https://github.com/NICE-DEV226/Dun.git
cd Dun

go test ./...
go test -race ./...
go vet ./...

# runnable gateway example (backend :3000, dun :8080)
go run ./examples/gateway/backend &
go run ./cmd/dun run -config examples/gateway/dun.yaml
curl -i localhost:8080/api/hello

# benchmark matrix
go test ./benchmarks -bench . -benchmem -benchtime=2s

Plugin examples with pre-built artifacts: security-header, deny-header, auth, cors — see docs/EXTENSIONS.md.

Status & limitations

Dun is pre-1.0 and experimental. The v0 contract is deliberately small; the following are known gaps, not hidden ones.

  • No request/response body API yet — RESPOND cannot emit a body; streaming is future work (RFC-0004).
  • No plugin signature verification or remote registry; artifacts are pinned by SHA-256 only.
  • No load balancing, service discovery or control plane — by design.
  • Proxy-Wasm compatibility is a research question, not an implemented layer.
  • Pooling applies only to artifacts without tables, globals or element segments.
