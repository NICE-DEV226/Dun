Dun

A Go-native programmable HTTP data plane
with a WebAssembly extension boundary.

  • go 1.27+
  • wazero

1Abstract

Dun explores whether a production-shaped HTTP data plane can stay small and auditable while delegating application-specific behavior to sandboxed WebAssembly extensions. The trusted core owns routing, proxying, configuration and lifecycle; extensions run under an explicit capability model with per-request isolation, resource limits and classified failure telemetry. This page summarizes the architecture, the extension contract, and measured costs — including where Wasm is, and is not, a good boundary for HTTP infrastructure.

2Architecture

Every request traverses a narrow trusted path. Plugins are consulted in order, each inside its own sandbox; decisions (continue, respond, reject, error) are explicit integers, not conventions.

Isolation

Fresh Wasm instance per request by default; opt-in instance pooling for pool-safe artifacts. Memory, timeout and concurrency are bounded per plugin.

Capabilities

Two-stage enforcement: manifests are checked against deployment policy at load time; ungranted host functions are not exported at instantiation.

Failure model

Traps, timeouts, cancellations and host-call errors are classified (trap, timeout, cancelled, …), recorded per plugin, and contained — the core keeps serving.

3Evaluation

Pipeline-level benchmarks isolate the extension boundary: the same pipeline machinery runs either a native Go extension or a Wasm-backed one performing identical work (one response-header write). Full methodology in docs/BENCHMARKS.md.

Under concurrency (b.RunParallel), pooled instantiation measures ~153µs/op and 68.7KB/op versus ~215µs/op and 144.2KB/op per-request — a ~29% latency and ~52% allocation reduction. Hot reload costs ~2.5ms per swap and is atomic. These numbers motivated RFC-0009: pooling is opt-in, restricted to artifacts whose state can be provably reset.

Finding. Wasm buys isolation and language freedom, not speed. For header-scale work it is a defensible trade; for microsecond-critical paths a native extension remains the right boundary. The honest cost is published rather than hidden.

4Reproduce

Requirements: Go 1.27+, no cgo, no external services for the tests.

git clone https://github.com/NICE-DEV226/Dun.git
cd Dun

go test ./...
go test -race ./...
go vet ./...

# runnable gateway example (backend :3000, dun :8080)
go run ./examples/gateway/backend &
go run ./cmd/dun run -config examples/gateway/dun.yaml
curl -i localhost:8080/api/hello

# benchmark matrix
go test ./benchmarks -bench . -benchmem -benchtime=2s

Plugin examples with pre-built artifacts: security-header, deny-header, auth, cors — see docs/EXTENSIONS.md.

5Status & limitations

Dun is pre-1.0 and experimental. The v0 contract is deliberately small; the following are known gaps, not hidden ones:

  • No request/response body API yet — RESPOND cannot emit a body; streaming is future work (RFC-0004).
  • No plugin signature verification or remote registry; artifacts are pinned by SHA-256 only.
  • No load balancing, service discovery or control plane — by design.
  • Proxy-Wasm compatibility is a research question, not an implemented layer.
  • Pooling applies only to artifacts without tables, globals or element segments.
